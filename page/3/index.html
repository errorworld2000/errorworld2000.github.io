ow架构

发表于 2025-09-16 更新于 2025-09-17 分类于 other Valine：
本文字数： 1.4k 阅读时长 ≈ 1 分钟

核心架构与 ECS（实体-组件-系统）

  • Overwatch 用 ECS 架构 管理复杂度

    • Entity 是一个 ID + 一组组件（Component，仅存储状态，无行为）

    • System 执行行为（Behavior），关注某些组件的组合（tuple / component-slice），在这些组件上做处理

  • 优点：将状态与行为分离，System 更纯洁可组合；组件只做数据存储，行为集中在 System 中

  • 多数 System 是纯函数式（只读组件），只有少数 System 修改状态

  • 单例组件（Singleton Component）用于存储那种全局共享但需要被多个 System 用的数据／状态，例如输入状态（键盘等），以减少 System 间耦合

  • Utility 函数用于封装共享行为（被多个 System 调用的小逻辑），要求依赖少数组件、低副作用，避免 System 之间互相调用

ECS 中的设计规范与权衡

  • 组件（Component）没有行为，System 尽量无状态

  • 如果 System 需要状态，改为放在 Singleton Component 中

  • 副作用严格控制：

    • “推迟执行”（deferred execution）机制：把某些副作用（例如创建实体、特效等）暂存到帧尾或某个统一阶段统一处理

    • 防止多个 System 在帧中间互相依赖造成脏状态或竞态行为

  • 实体创建与销毁处理谨慎：通常 “销毁推迟到帧末端” 安全；但 “创建推迟” 有可能造成某些 System 在同一帧中无法获取新实体的问题

网络同步 / Netcode 机制

  • 预测 & 回滚（Prediction & Reconciliation）

    • 客户端响应用户输入时立即做预测（比如移动、技能释放），不等服务器确认。

    • 用固定帧率／命令帧（command frames）制度，客户端和服务器都按这些帧同步模拟。

    • 客户端保存输入历史 + 移动状态历史，以便在收到服务器确认后回滚到最后一个确认帧，然后重放客户端输入直至当前帧。

  • 输入滑动窗口 + 丢包补偿

    • 客户端在每个发送包里包含从最后确认以来的所有输入帧，保证丢包时输入不遗失。

    • 服务器有一个缓冲区用来接受这些输入／补充丢失的输入。

  • 延迟 / 缓冲 /时间膨胀（Buffering / Time Dilation）

    • 如果网络不稳定（高延迟 + 丢包 + 抖动），客户端会加速（time dilation）或扩大缓冲区，以减少预测错误造成卡顿体验。恢复稳定后再缩小这些。

  • 命中判定（Hit Registration）

    • 客户端可能预测子弹命中，但服务器是最终权威。

    • 对于远端实体（non-local），使用插值；服务端回滚远端实体状态以做准确命中判断。

    • 在某些高延迟情况下，如果 Ping 太大，会放弃客户端预测，直接等待服务器确认。

总结的关键教训／设计原则

  • 架构要为可维护性、可扩展性服务，ECS + 严格准则（组件无行为，System少状态）帮助控制复杂度

  • 网络同步设计里，预测 + 回滚是必须的，以保证响应性，同时要设计好丢包、延迟、预测错误的补偿机制

  • Utility、Singleton、Deferred 操作这些技术是用来缓解 System 之间耦合和帧内副作用带来的问题
