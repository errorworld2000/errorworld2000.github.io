Git 协作流程核心摘要

1. 各分支核心职责 (Core Responsibilities of Each Branch)

分支类型 生命周期 核心职责
master 永久 只读。永远指向最新已发布版本的代码快照。是生产环境代码的最终来源。
release/x.y.z 长期，随版本存在 开发、测试、修复的主战场。所有面向该版本的 feature 和 hotfix 都合并到这里。新版本从上一个 release 分支创建。
feature/xxx 短期，随任务生灭 开发新功能。必须从其目标 release 分支创建，并最终合并回该 release 分支。
hotfix/xxx 短期，紧急修复用 修复线上紧急 Bug。从出问题的 release 分支创建，修复后合并回该分支，并必须同步到所有后续的 release 分支中。

2. 个人开发标准流程 (Standard Workflow for Individual Developers)

这是一个开发者从接到任务到提交 PR 的完整步骤。

第一步：同步并创建分支

从你任务对应的 目标 release 分支 拉取最新代码，并创建你的功能分支。

第二步：本地开发与提交

在你的 feature 分支上进行编码，并进行多次原子化的提交。

第三步：整理提交记录 (提交 PR 前的关键一步)

在发起 PR 前，使用交互式 rebase (rebase -i) 来清理你的提交历史，将多个零碎的 commit 合并成一个或几个有意义的 commit。

第四步：推送并创建 PR

由于 rebase 修改了 git 历史，你需要强制推送到你的远程分支。

最后，在 GitHub / GitLab 等平台上，从你的 feature/your-task-name 分支向目标 release/1.11.0 分支发起 Pull Request。

3. PR 审查与合并流程 (PR Review and Merge Process)

这是项目维护者 (Maintainer) 或团队负责人收到 PR 后的操作流程。

第一步：代码审查 (Code Review)

  • 逻辑审查：检查代码的业务逻辑、健壮性和潜在风险。
  • 规范审查：检查代码风格、命名是否符合团队规范。
  • 目标分支确认：确保 PR 提交的目标分支是正确的 release 分支。
  • 至少需要一名或多名成员 Approve。

第二步：合并前检查

  • CI/CD 状态：确保所有自动化检查（如测试、构建）都已通过。
  • 提交历史：检查 PR 的 commit 记录是否已按要求整理干净。如果未整理，要求提交者返回上一步（个人流程的第三步）进行 rebase。
  • 合并冲突：确保 PR 没有合并冲突。如有冲突，要求提交者在本地解决冲突后再提交。

第三步：执行合并 (推荐在 Git 平台 UI 上操作)

强烈推荐使用以下两种合并策略，严禁使用 Merge Commit。

合并方式 操作方式 优点
Squash and Merge (推荐) 在平台点击 “Squash and Merge” 按钮。 将 PR 内所有 commit 合并成一个，生成一个非常干净的 release 分支历史。
Rebase and Merge (可选) 在平台点击 “Rebase and Merge” 按钮。 将 PR 内已整理好的 commit 按顺序追加到 release 分支，保持线性历史。

第四步：清理分支

PR 合并后，应立即删除已被合并的 feature 分支，保持仓库整洁。
